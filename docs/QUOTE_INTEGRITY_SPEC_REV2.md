# ТЗ: Quote Integrity Monitor — Rev 2.1

**Статус:** draft на утверждение оператором
**Репозиторий:** `traderbybit`
**Флаг:** `QUOTE_INTEGRITY_ENABLED` — по умолчанию `false`
**Заменяет:** addendum «IQ Option vs TradingView — Independent Quote Integrity Monitoring»
в части, противоречащей §1 (посылка о существующих интеграциях).

## 0. Контекст и исправление посылки

Приложение — исследовательская платформа Bybit + paper trading, 8 независимых
виртуальных аккаунтов (по одному на стратегию, enforced миграцией
`2026_10_18_010000_enforce_eight_primary_accounts_and_widen_quality.php`).
Единственный источник рыночных данных — **Bybit v5**:

- REST: `app/MarketData/Infrastructure/Bybit/BybitRestClient.php`
  (`/v5/market/kline` с reverse-пагинацией, `/tickers`, `/orderbook`; backoff на 429/5xx/`retCode=10006`);
- WebSocket: `app/MarketData/Application/MarketStreamSupervisor.php` +
  `app/MarketData/Infrastructure/WebSocket/PhrityWebSocket*` (ingress-фильтр `confirm=true`);
- таблицы: `market_context_snapshots` (bid/ask/…, `observed_at` timestamptz(3)),
  `market_candles`, `virtual_positions`, `virtual_executions`, `strategy_observations`.

В репозитории **нет** интеграций, таблиц или сервисов IQ Option и TradingView.
Официальных публичных котировочных API у обоих провайдеров нет.

Исходная цель проекта — выявлять межисточниковые расхождения котировок (в том числе
наблюдение IQ Option vs TradingView, сделанное оператором вне приложения) — сохраняется,
но разделяется на два уровня:

- **Level 1 (делается сейчас):** внутренняя целостность данных Bybit в рамках
  собственного ingestion-конвейера приложения.
- **Level 2 (отложено):** независимое межисточниковое сравнение — начинается только
  после подтверждённого, легально допустимого второго источника (или легального импорта
  материалов расследования, §5).

Ретроспективный инцидент IQ Option/TradingView **никогда не будет доказан автоматически**
системой: он произошёл вне приложения. Доступный путь — ручной импорт сохранённых
оператором материалов (§5) с честной оценкой полноты доказательств.

Система обязана в UI явно показывать `CROSS_SOURCE_UNAVAILABLE`, пока второй источник
не подтверждён, — чтобы не создавать ложное чувство, что первоначальная задача решена.

## 1. Зафиксированные архитектурные решения (не пересматриваются)

| Решение | Формулировка |
|---|---|
| Q0 — source-capability gate | Timebox 2–3 рабочих дня. Результат: матрица возможностей источников + документированный вердикт допуска каждого. Никаких интеграций в Q0. |
| L1 — внутренний монитор | Повторное использование существующего Bybit ingestion. Проверки свечей, REST/WS, задержек, дублей. Неизменяемые доказательства, отдельная страница UI. |
| L2 — межисточниковое сравнение | Отдельный этап после гейта. Контракт источника фиксируется в §4.2 сейчас (polling-only), реализация — позже. До гейта система не заявляет, что межисточниковая проверка работает. |
| Флаг | `QUOTE_INTEGRITY_ENABLED=false` по умолчанию. OFF → нет сбора, нет фоновых задач, API возвращает `503 FEATURE_DISABLED`, страница UI открывается и показывает состояние `FEATURE_DISABLED`. Торговый конвейер не затрагивается ни в одном состоянии. |
| Измерительный период | Прежде чем фиксировать retention — ограниченное измерение (§3.4) с разрешения оператора, с лимитом диска и TTL. Неопределённые лимиты → измерительный режим не запускается. Основной режим — закрытые минутные свечи. Tick-level только для открытого расследования. |
| Контракт источника | Минимальный polling-порт `QuoteSourceProvider` (§4.2). Не универсальная мультибиржевая платформа; streaming добавляется отдельно при реальной необходимости. |
| Независимость от торговли | Монитор не меняет стратегии, сигналы, направление, риск, expiry, sizing; не трогает 8 paper-аккаунтов и их историю; не размещает реальных ордеров; не переписывает исторические исходы. |

## 2. Q0 — Source-capability gate

**Ограничение по времени:** 2–3 рабочих дня. По истечении timebox gate считается
пройденным или проваленным по уже собранному — исследование не продлевается молча.

**Deliverable:** `docs/source-capability-matrix.md` (+ копия в evidence bundle).

Для каждого кандидата-источника (Bybit REST, Bybit WS, TradingView, IQ Option, иные):

| Поле | Примечание |
|---|---|
| Источник | название |
| Статус допуска | `ADMITTED` / `REJECTED` / `UNDETERMINED` |
| Метод получения | официальный REST / официальный WS / пользовательский экспорт / иное |
| Timestamp precision | что заявлено и что подтверждено |
| Семантика цены | bid/ask/last/candle; OTC-специфика |
| Исторические данные | доступны ли, глубина, формат |
| Rate limits | заявленные/наблюдаемые |
| Юридический статус | ToS: разрешено / запрещено / неясно; кто проверял, когда |
| Provenance | как получено подтверждение |

Правила gate:

- `REJECTED` или `UNDETERMINED` → источник не подключается в L2. Без исключений.
- Скрейпинг, недокументированные приватные эндпоинты, обход access-control —
  запрещены явным текстом и не рассматриваются как «временное решение».
- Q0 не пишет интеграционного кода и не создаёт таблиц.
- Если источник поставляет данные только через подписку оператора — фиксируется,
  что доступ обусловлен подпиской, и её существование проверяется до L2.

**Приёмка Q0:** матрица заполнена; по каждому источнику есть вердикт с обоснованием;
решения оператора по допуску подтверждены письменно (в PR/review).

## 3. Level 1 — внутренний монитор целостности Bybit

### 3.1 Проверки

| ID | Проверка | Логика |
|---|---|---|
| C1 | Candle continuity (событийная + состоянием) | Обязателен **событийный** мониторинг: в момент обнаружения гэпа (в потоке gap-recovery `MarketStreamSupervisor`) фиксируется событие пропуска — `detected_at`, границы пропуска, символ, результат восстановления, оставшиеся пропуски — и сохраняется неизменяемо (`qim_gap_events`). Это принципиально: если gap-recovery успел восстановить свечу, проверка состояния `market_candles` увидит непрерывную историю, и факт пропуска исчезнет из наблюдаемого состояния. Периодическая проверка состояния БД (гэпы относительно ожидаемых интервалов по включённым символам) — **дополняет** событийный мониторинг, но не заменяет его. |
| C2 | REST ↔ WS согласованность с provenance | Сравнение **только закрытых** свечей: одинаковый symbol, interval, подтверждённость (`confirm=true`), сопоставимые поля OHLC. Достаточно двух одинаковых строк в `market_candles` недостаточно — должна быть доказана разная принадлежность каналов. Минимальный обязательный состав записи наблюдения: `provider`, `channel` (`REST` \| `WS`), инструмент, интервал, время свечи, OHLC, флаг подтверждённости закрытия, времена получения (см. C3). Перед реализацией Codex проверяет в текущей архитектуре, какие из этих полей реально сохраняются в `market_candles`/`market_context_snapshots` и **не теряется ли provenance канала** при записи в общую таблицу; если теряется — фиксируется в задании на миграцию/дозапись (например, `channel`-колонка или отдельные строки наблюдений QIM). Расхождение классифицируется как `CHANNEL_INCONSISTENCY` (проблема каналов/ingestion) и **не** является доказательством ошибки котировок биржи — оба канала проходят через одну инфраструктуру Bybit; в UI выводится дисклеймер. |
| C3 | Latency & freshness с корректной семантикой времени | Для **WS**: `provider_event_time` (если передан) и `local_received_at` — раздельно. Для **REST**: отдельно фиксируются `request_sent_at` и `response_received_at`; время открытия/закрытия свечи **не** является временем получения ответа и не подменяет его. Разность `response_received_at − request_sent_at` — round-trip с учётом очереди/обработки; разность «время свечи vs receipt» — возраст данных, **не** «чистая сетевая задержка». Называть значения сетевой задержкой без обоснования запрещено. Возраст наблюдения и stale-пороги — конфигурируемые, по умолчанию привязаны к интервалу свечи. |
| C4 | Дубликаты с сохранением конфликтов | Не полагаться только на UUIDv5/unique index бизнес-таблиц. Логическая идентичность наблюдения определяется явно (например, `provider + channel + symbol + interval + candle_time`); способ хранения наблюдения QIM должен позволять зарегистрировать повторную попытку **до** или **независимо** от отбраковки уникальным индексом бизнес-таблиц. Классы: `DUPLICATE_EXACT` (идентичное содержимое, совпадает payload hash), `DUPLICATE_CONFLICTING` (тот же логический ключ, другое содержимое — сохраняется достаточно информации о конфликте: оба payload hash и полная вторая версия, **без перезаписи** первого наблюдения), `DUPLICATE_IDENTITY_CONFIG` (id-конфликт из-за изменения конфигурации/версии). Существующие таблицы и решения paper trading **не изменяются**; детект — наблюдательный. Иначе монитор видит только те дубли, которые уже пропустила защита идемпотентности. |
| C5 | Синхронизация часов | Состояние NTP и оценка смещения (например, через `chronyc`/`ntpq`, если доступно в контейнере). Если недоступно — `CLOCK_SYNC_UNKNOWN`, сравнения помечаются пониженной уверенностью. |
| C6 | Ошибки ingestion | 429, `retCode=10006`, reconnect'ы WS, падения gap-recovery — уже логируются; монитор агрегирует их в инциденты. |

### 3.2 Модель времени

Для каждого наблюдения сохраняются раздельно:

- `provider_event_time` (если источник его передаёт; иначе явно отсутствует);
- `local_received_at` (UTC); для REST дополнительно `request_sent_at`;
- `clock_sync_state` + `clock_offset_estimate_ms`;
- `normalization_rule_version`.

Точность представления timestamp (3 мс) **не** утверждает реальную синхронизацию
часов — это разные утверждения, и код/документация не смешивают их.

### 3.3 Хранение доказательств (append-only) и граница с retention

Новые таблицы (additive-миграции, стилизация под существующие: анонимные классы,
timestamptz(3), UUID v5 для идемпотентных ключей):

- `qim_observations` — сырые наблюдения (provider, **channel**, symbol, interval,
  candle time, OHLC, confirmed, `request_sent_at`/`response_received_at` для REST,
  `provider_event_time`/`local_received_at`, checksum raw-источника, quality-статусы).
  **Insert-only.**
- `qim_gap_events` — события обнаружения пропусков свечей (C1): момент обнаружения,
  границы пропуска, результат восстановления, остаточные пропуски. Insert-only.
- `qim_comparisons` — пара наблюдений, разность, skew, версия правила сравнения,
  классификация, причина сопоставимости/несопоставимости. Результаты **версионируются**:
  исправление = новая версия, старая сохраняется.
- `qim_incidents` — агрегаты инцидентов, статус, severity, приоритет. Текущее
  состояние инцидента **изменяемо**, но только через операции жизненного цикла (§8).
- `qim_incident_events` — append-only аудит переходов и решений.
- `qim_evidence_files` — импортированные материалы (§5): оригинальные байты,
  SHA-256, provenance-класс, declared source/timezone, отметка отсутствующих метаданных.
- `qim_alerts` — алерты с дедупликацией (§7).
- `qim_purge_audit` — журнал планового удаления (§3.4): что, почему, когда, кем/чем.

**Граница неизменяемости и retention (явно):**

1. Запрет изменения и удаления действует **в течение срока хранения**: зашитый на уровне
   БД (права приложения: INSERT на `qim_observations`/`qim_gap_events`/`qim_incident_events`/`qim_evidence_files`,
   без UPDATE/DELETE; UPDATE разрешён только `qim_incidents` в рамках жизненного цикла;
   DELETE — только отдельной purge-роли/джобе).
2. Плановое истечение TTL — **отдельная контролируемая операция** с записью в
   `qim_purge_audit` (что удалено, правило retention, версия конфига, причина).
   Несанкционированный DELETE вне purge-процедуры считается нарушением и должен
   обнаруживаться проверкой целостности (evidence-verification).
3. Три класса данных не смешиваются: неизменяемые исходные наблюдения
   (`qim_observations`, `qim_gap_events`, `qim_evidence_files`, `qim_incident_events`) ·
   версионируемые результаты сравнений (`qim_comparisons`) ·
   изменяемое текущее состояние инцидента (`qim_incidents`) с append-only историей переходов.

Исправление маппинга или классификации — **новая версия/строка аудита**, никогда
не перезапись исходного наблюдения.

### 3.4 Sampling и измерительный период

- Основной режим: сэмплинг закрытых **1m** свечей по включённым символам.
- **Guard неопределённых лимитов:** измерительный режим **не запускается**, если не заданы
  `QUOTE_INTEGRITY_MEASUREMENT_DISK_CAP_GB` и `QUOTE_INTEGRITY_MEASUREMENT_TTL_DAYS`
  (запуск → отказ с машиночитаемой ошибкой `MEASUREMENT_LIMITS_UNSET`).
- Измерительный период: **7 дней**, только с явного разрешения оператора
  (`QUOTE_INTEGRITY_MEASUREMENT_MODE=true`), с жёстким лимитом диска и TTL хранения.
  По истечении — отчёт (`qim:measurement-report`): объём, задержки, частота
  срабатываний, стоимость; оператор принимает решение о retention
  (`QUOTE_INTEGRITY_RETENTION_DAYS`) и постоянном сборе. Без решения — сбор
  останавливается, данные удаляются через purge-процедуру с `qim_purge_audit`.
- Tick-level: включается только для конкретного открытого расследования
  (per-investigation override, с TTL), не как режим по умолчанию.

### 3.5 Семантика флага

`config/quote_integrity.php` + env `QUOTE_INTEGRITY_ENABLED` (default `false`):

- OFF: нет регистраций scheduler/queue-джоб, нет записи наблюдений,
  read- и write-API → `503 FEATURE_DISABLED` с машиночитаемым полем
  `error.code = "FEATURE_DISABLED"`. **Браузерный маршрут страницы при этом
  доступен** (обслуживается фронтенд-бандлом) и рендерит состояние `FEATURE_DISABLED`
  на основе ответа API — пользователь гарантированно видит предусмотренное состояние.
  Торговый конвейер, 8 аккаунтов, paper trading — не затронуты.
- Включение и выключение — только оператором; выключение прекращает **новый** сбор,
  **не** удаляет собранные доказательства.

Консоль: `qim:sample-bars`, `qim:run-checks`, `qim:measurement-report`,
`qim:purge-expired` — все no-op/отказ при флаге OFF.

### 3.6 Классификации Level 1

- `MATCHED` — значения согласованы в пределах конфигурируемого допуска.
- `CHANNEL_INCONSISTENCY` — REST/WS (или иные каналы одного провайдера) расходятся
  на сопоставимых закрытых свечах.
- `STALE_DATA` — наблюдение старше порога.
- `CLOCK_SYNC_UNKNOWN` / `TIMESTAMP_UNRELIABLE` — часы не верифицированы.
- `DUPLICATE_EXACT` / `DUPLICATE_CONFLICTING` / `DUPLICATE_IDENTITY_CONFIG` — §3.1 C4
  (единые названия во всех слоях: БД, API, UI, тесты).
- `INSUFFICIENT_EVIDENCE` — данных не хватает для вывода (fail-closed).

Допуски конфигурируются версионируемо (`config/quote_integrity.php`, поле
`rules_version`) и **не** маркируются как «валидированные», пока нет калибровочных данных.

## 4. Level 2 — отложен; контракт фиксируется сейчас

### 4.1 Условия старта L2

1. Q0-гейт пройден; источник имеет вердикт `ADMITTED`.
2. Подтверждён легальный метод получения (существующая подписка оператора или
   официальный интерфейс).
3. Отдельное решение оператора о начале L2.

### 4.2 Контракт `QuoteSourceProvider` (минимальный, polling-only)

Контракт на старте — **только polling**. Streaming не определяется заранее:
он добавляется отдельным изменением, когда появится допущенный источник,
фактически требующий streaming (`capabilities()` при этом сообщает
`supportsStreaming`, но интерфейс его не включает). Универсальная мультибиржевая
платформа не проектируется.

```php
interface QuoteSourceProvider
{
    public function capabilities(): SourceCapabilities;

    /**
     * Результат операции целиком отделён от статуса отдельных полей котировки.
     * NO_DATA  — запрос корректен, данных за момент нет;
     * UNSUPPORTED — возможность не поддерживается источником (по capabilities);
     * ERROR    — ошибка получения (сеть, лимит, авторизация) с причиной.
     */
    public function fetchQuote(ProviderInstrumentRef $instrument, CarbonInterface $at): FetchOutcome;
}

final class FetchOutcome
{
    public FetchStatus $status;      // OK | NO_DATA | UNSUPPORTED | ERROR
    public ?NormalizedQuote $quote;  // заполнен только при OK
    public ?string $errorReason;     // для ERROR / UNSUPPORTED
}

final class SourceCapabilities
{
    public bool $supportsPolling;
    public bool $supportsStreaming;  // информационно; интерфейс streaming не определён в Rev 2.1
    public bool $supportsHistory;
    public array $priceTypes;        // bid, ask, last, candle_ohlc...
    public ?string $timestampPrecision;
    public ?string $rateLimitNotes;
}
```

`NormalizedQuote`: provider ids, оба timestamp (если доступны), bid/ask/mid/last/OHLC
**только при фактической доступности**; каждое поле — `(value, field_status)` со
статусом `VALUE` / `UNAVAILABLE(reason)` / `NOT_SUPPORTED`. `NULL` **не** превращается
в нулевую цену и **не** используется для расчёта производных (mid из last и т.п.);
производные значения допустимы только из фактически доступных компонентов и
помечаются как вычисляемые.

Нормализация **не** перезаписывает raw: оригинал сохраняется в `qim_observations`
с checksum.

### 4.3 Межисточниковая классификация (появляется в L2)

`MATCHED` / `EXPECTED_PROVIDER_DIFFERENCE` / `TIMESTAMP_MISMATCH` /
`INSTRUMENT_MISMATCH` / `STALE_DATA` / `CONFIRMED_DISCREPANCY` /
`REPEATED_ANOMALY` / `SUSPECTED_SYSTEMATIC_ANOMALY` / `INSUFFICIENT_EVIDENCE`.

Разделены detection и attribution: система устанавливает факт расхождения,
не устанавливает причину. Манипуляция не выводится никогда.

## 5. Ручной импорт материалов (ретро-инцидент) — доступен до L2

Назначение: зафиксировать материалы оператора по случаю IQ Option vs TradingView
(и любым иным), не дожидаясь живого второго источника.

- Provenance-класс (явная метка): `ORIGINAL_EXPORT` / `SCREENSHOT` /
  `OPERATOR_TRANSCRIBED` / `SYNTHETIC_TEST_FIXTURE`.
- Для каждого файла: оригинальные байты (неизменённые), SHA-256, `uploaded_at`,
  заявленный источник, заявленная таймзона, список отсутствующих метаданных.
- **Ограничения загрузки (до реализации, конфигурируемы с дефолтами в коде):**
  максимальный размер файла (default 20 MB) — при превышении API возвращает
  `413` с машиночитаемым кодом `EVIDENCE_TOO_LARGE`; разрешённые форматы —
  whitelist (`png`, `jpg`, `jpeg`, `pdf`, `csv`, `json`, `txt`), иное → `415 EVIDENCE_FORMAT_NOT_ALLOWED`;
  хранение вне webroot, доступ к чтению — только авторизованным операторам
  (write-API — с исследовательским токеном, см. §9); файлы отдаются только через
  защищённый endpoint с проверкой прав.
- SHA-256 доказывает неизменность файла **после** фиксации, не подлинность котировок;
  скриншот подтверждает отображённое в интерфейсе, не официальные рыночные данные.
  Эти дисклеймеры — обязательны в UI детали расследования.
- Статусы расследования импортированного случая: `INSUFFICIENT_EVIDENCE` (по умолчанию),
  `UNDER_REVIEW`, `OPERATOR_CONFIRMED_DISCREPANCY` (только решением оператора с
  обоснованием — статус означает решение человека, **не** автоматическую проверку
  подлинности источника). Загрузка файла **никогда** не переводит статус автоматически.

## 6. UI — страница «Quote Integrity Monitor»

Отдельная страница фронтенда (Vue 3 + Quasar, по образцу существующих Research-страниц;
роут в `frontend/src/router/index.ts`; API — `/api/v1/quote-integrity/*`).

Состояния страницы, отображаемые явно:
`FEATURE_DISABLED` · `MEASUREMENT_MODE_ACTIVE` · `CROSS_SOURCE_UNAVAILABLE` ·
`INSUFFICIENT_EVIDENCE` · `CLOCK_SYNC_UNKNOWN`.

**Summary metrics (L1):** всего сравнений; согласованных; `CHANNEL_INCONSISTENCY`;
дубликаты по классам; пропуски свечей (из `qim_gap_events`, включая
восстановленные — восстановление не скрывает факт пропуска); stale-наблюдения;
инциденты по статусам; покрытие данных; доля наблюдений с валидной синхронизацией
часов; длительность измерительного периода и объём хранения. Метрики L2 (confirmed
discrepancies, financial impact) **не отображаются до гейта** — вместо них блок
`CROSS_SOURCE_UNAVAILABLE` с пояснением.

**Историческая таблица с фильтрами:** диапазон дат/времени, инструмент, провайдер,
канал (REST/WS), классификация, разность (abs/rel), timestamp skew, связанный исход
сделки (L1: только если инцидент ingestion коснулся данных сделки), статус
расследования.

**Деталь расследования:** оба наблюдения с provenance (provider, **channel**) и checksum;
синхронизованная таймлайн-лента (provider time vs receipt time; для REST —
request/response); вычисленные разности; raw-доказательства (ссылка на импортированный
файл, если есть); история классификаций и решений оператора; ссылка на исходную
запись анализа. Наблюдаемое и выведенное — визуально разделены;
`UNKNOWN` / `UNVERIFIED` / `INSUFFICIENT_EVIDENCE` не скрываются.

## 7. Алерты

Только внутри приложения (внешние каналы не вводятся; в существующей кодовой базе
надёжного notification-канала нет — фиксируем: доставка внешняя недоступна, алерт
виден на странице и в API).

Правила (пороги конфигурируемы, версионируются, **не** подстраиваются постфактум):

- один confirmed/incident выше порога оператора;
- повтор инцидентов в окне наблюдения;
- кластер по одному инструменту;
- персистентная задержка/stale провайдера;
- пропуск данных (в т.ч. восстановленные гэпы по правилу «частые восстановления = сигнал»);
- ошибка маппинга инструмента (в L2);
- повторяющийся инцидент, потенциально влияющий на данные сделок.

Payload алерта: alert id, severity, инструмент, first/last observed, число
квалифицирующих наблюдений, наблюдённые разности, связанные trade id (если есть),
ссылки на доказательства, версия правила, текущий статус расследования.
Дедупликация по `(rule_version, rule_key, incident_group, window)`; каждое
наблюдение сохраняется, отдельные уведомления — нет.

## 8. Жизненный цикл инцидентов

`NEW → INVESTIGATING → EXPLAINED | UNRESOLVED | CLOSED`

Каждый переход — append-only запись в `qim_incident_events`: прошлый/новый статус,
timestamp (UTC), актёр, объяснение/резолюция, ссылки на доказательства, версии правил
и конфигурации.

- `EXPLAINED` требует документированного, подтверждённого доказательствами объяснения.
- `CLOSED` **не** означает, что расхождения не было.
- Приоритизация может быть автоматической; обвинение провайдера — никогда.

## 9. Ограничения полномочий (неприкосновенно)

Монитор **не** может: размещать реальные ордера; включать реальный trading;
менять стратегии/сигналы/направление/risk/expiry/sizing; переписывать исторические
исходы под референс-фид; сбрасывать или мутировать 8 paper-аккаунтов
(`paper_accounts` с `is_primary`/`primary_strategy_id`); вводить торговую
авторитетность через AI/внешние модели.

Любое будущее изменение торгового поведения — отдельная спецификация, проспективная
валидация, явное одобрение оператора.

**Предусловие write-API:** привести в соответствие документации состояние
`App\Http\Middleware\RequireResearchToken` (сейчас no-op pass-through, при этом
`docker/README.md` заявляет `X-Research-Token` для POST) — до включения write-API QIM.
Это отдельный маленький changeset, не блокирующий Q0.

## 10. Миграции и деплой

- Только additive, обратимые в dev; в проде `down()` не применяется.
  Проблемы со схемой — forward-fix по документированной процедуре (шаблон:
  deployment-state recovery из текущего work-in-progress по деплою).
- Флаг по умолчанию OFF; включение — отдельный операторский шаг после приёмки.
- Порядок включения: (1) deployment-recovery фиксации независимо проверен;
  (2) миграции совместимы, здоровье сервисов подтверждено; (3) полный регрессионный
  набор; (4) сбор и алерты проверены в non-production; (5) выключение флага
  останавливает сбор и не удаляет данные.
- Откат = выключение флага. Миграции не откатываются в проде.
- Вне области: `ECONOM / ECONOM-group` и все прочие Docker-ресурсы рабочей папки.

## 11. Тестирование

Обязательные кейсы (PHPUnit, в стиле существующего `tests/`):
Unit + Feature, SQLite для изолированных; Integration — gated `RUN_BYBIT_INTEGRATION`):

1. Идентичные наблюдения → `MATCHED`.
2. Известная разница значений → `CHANNEL_INCONSISTENCY` (закрытая свеча, с
   подтверждённым разным `channel`).
3. Skew timestamps / задержка приёма → корректная классификация, не ложный `MATCHED`.
4. Stale-наблюдения → `STALE_DATA`; REST round-trip vs возраст свечи различаются в классификации.
5. Дубликаты: точный / конфликтующий / identity-config — счётчики и классы;
   **конфликтующий дубль сохраняет обе версии payload, несмотря на unique index бизнес-таблиц**.
6. Гэп, восстановленный до проверки состояния → событие в `qim_gap_events` сохранено
   и видно (проверка состояния БД пропуск не «лечит»).
7. Отсутствующие bid/ask/OHLC → поля `UNAVAILABLE(reason)`, не нули, не mid из last.
8. Concurrent writes / повторная запись (по образцу `scripts/concurrency_worker.php`).
9. Часы `CLOCK_SYNC_UNKNOWN` → сравнения с пометкой уверенности.
10. Неполные данные → `INSUFFICIENT_EVIDENCE` (fail-closed).
11. Append-only: попытка UPDATE/DELETE наблюдения отклонена на уровне прав БД;
    purge-процедура пишет `qim_purge_audit`; аудит-история полна.
12. Флаг OFF: нет джоб, нет записи, API `503` с `error.code=FEATURE_DISABLED`,
    страница открывается и рендерит состояние, торговые тесты зелёные.
13. Измерительный режим без заданных disk cap/TTL → отказ `MEASUREMENT_LIMITS_UNSET`.
14. Auth: write-API недоступно без токена; read-страница за Nginx basic auth;
    импорт доказательств соблюдает лимиты размера/формата (`413`/`415`).
15. UI: фильтры, детали, состояния ошибок (frontend `node --test` по образцу).
16. Провал провайдера/реста rate-limit → C6 инциденты, восстановление.
17. Regression: полный существующий набор (`phpunit`, Pint, frontend tests, Go-тесты,
    `scripts/verify-system.sh`) — без изменений поведения 8 аккаунтов
    (`AccountSafetyRegressionTest`, `PrimaryAccountMigrationRehearsalTest`).

Фикстуры: golden — из фактических захватов; синтетика допустима только для
краевых случаев алгоритмов и **обязана** меткой `SYNTHETIC`. Прохождение
синтетических тестов никогда не является доказательством аномалии провайдера.

## 12. Evidence bundle

Каждый значимый changeset/выпуск флага сопровождается `reports/evidence/qim_*.json`:

- commit SHA; checksums входных данных; Q0 source-capability matrix;
- версия правил сравнения и конфигурации допусков;
- команды тестов + exit codes + stdout/stderr;
- скрипты генерации фикстур; expected vs actual;
- негативные контролы; хеши воспроизводимости;

## 13. Приёмка по этапам (Definition of Done)

| Этап | Объективный критерий завершения |
|---|---|
| Этап 0 | Этот документ утверждён оператором и закоммичен в `docs/`. |
| Q0 | `docs/source-capability-matrix.md` существует; по каждому источнику вердикт с обоснованием; решения оператора зафиксированы. |
| L1 | На реальных данных работают C1–C6; гэпы фиксируются событийно и переживают gap-recovery; каждое наблюдение несёт provenance канала; конфликтующие дубли сохраняют обе версии; доказательства воспроизводимы из `qim_*`; страница UI показывает метрики, фильтры, детали, все честные состояния; флаг OFF по умолчанию; полный регресс зелёный; 8 аккаунтов и торговые правила неизменны. |
| Измерительный период | 7-дневный отчёт объёма/задержек/стоимости выдан; решение по retention принято оператором и закодировано (или сбор остановлен); удаление — только через `qim_purge_audit`. |
| L2 | Источник `ADMITTED`; сравнение учитывает оба timestamp, семантику цены, market type, provenance канала/источника; расхождения воспроизводимы из сохранённых пар наблюдений; `CROSS_SOURCE_UNAVAILABLE` исчезает только после гейта. |
| Ретро-импорт | Материалы сохранены с provenance и SHA-256 в пределах лимитов формата/размера; полнота оценена без выдуманных значений; статус — `OPERATOR_CONFIRMED_DISCREPANCY` только решением оператора. |

## 14. Вне области (Не делать)

- Live-интеграции IQ Option / TradingView до Q0-гейта `ADMITTED`.
- Автоматические обвинения провайдера; «финансовый ущерб» без подтверждённых данных.
- Изменения торговых правил, стратегий, paper-счетов, реальный trading.
- Внешние notification-сервисы.
- Универсальная мультибиржевая платформа; преждевременный streaming-контракт.
- Расширение этой рамки без новой явной причины и ревизии документа.
